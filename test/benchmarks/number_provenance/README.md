# 数字溯源基准

`cases.json` 给 `packing_assistant/tools/number_provenance.py` 打分：模型驱动的一轮（`civil --mode model`）里，模型回复中的每个工程量和条款号，是否都能在本轮看得见的东西里找到出处。全部用例为本基准编写，不含客户资料；标了 `live-` 的用例来自本机小模型（Ollama `qwen2.5:3b`）的真实输出。

```bash
python scripts/eval_number_provenance.py --variant all    # 消融表：每个机制贡献了什么
python scripts/eval_number_provenance.py --show           # 列出漏报和误报
python scripts/eval_number_provenance.py --check          # CI 下限 P ≥ 0.95、R ≥ 0.95（npm run check 里的 number-provenance-bench）
```

## 标注口径

- `evidence`：本轮合法看到的全部文字——用户原文、CIVIL.md、工具结果（JSON 文本）、知识库摘录、读过的工地文件。
- `draft`：模型想说的话。
- `untraced`：`draft` 里**没有出处、必须报出来**的数量（原文子串）；`clauses` 同理，是没有出处的条款号。
- `draft` 里其余的数都**不许报**。误报和漏报一样要紧：护栏一误报，模型就被要求改写掉真数字，用户也学会无视警告。

检查只回答「这个数在不在证据里」，不回答「这个数对不对、标签贴得对不对」。实测里小模型把工具结果的裸键 `payload_kg`（柜体额定载重）说成「货物总重」——数字有出处、含义是错的，这一类靠的是不给模型裸键（`model_loop._pack_plan` 只给带中文标签的 report），不靠这个基准。

## 当前数字（37 例，35 个必报项，20 份干净稿）

| variant | P | R | 说明 |
| --- | --- | --- | --- |
| exact_only | 0.729 | 1.000 | 只认一模一样的数：四舍五入、百分数、换算全被误报 |
| +rounding | 0.761 | 1.000 | 182.6 → 约 183 |
| +percent | 0.897 | 1.000 | 0.4043 ↔ 40.4% |
| +scale（现行） | 1.000 | 1.000 | 1350 kg ↔ 1.35 吨、20 万元 ↔ 200000 元 |
| 去掉型号/标准号遮罩 | 1.000 | 0.971 | 「JGJ 130」会替「130 cm」作证 |
| 去掉计数分族 | 1.000 | 0.914 | `"n_rows": 4` 会替「4 个柜」作证 |
| 去掉条款号检查 | 1.000 | 0.914 | 编出来的「第4.3.1条」放过去 |

同一个检查也用在整篇文稿上（`civil review <文稿>`）。短回复的用例测不出整篇文稿的毛病：第一次拿它扫真实日报草稿，就量出「## 2 天气」被读成 2 天（P 0.917）、「第7.2条」又被当裸小数报一遍（P 0.946），两类都已有用例。

## 加用例

先加用例、跑 `--variant all` 看数字，再决定要不要动规则。两类最值得补：

1. **真模型的输出**：`civil --mode model exec --jsonl` 跑本机模型，`guard.flagged` 报出来的、以及你看回复发现该报没报的，都原样收进来，`id` 以 `live-` 开头并在 `note` 里写明来源。
2. **会「洗」数字的证据**：证据里有个不相干的数恰好等于模型编的数（行数、耗时、标准号、柜型代码）。每加一种，就看对应的消融项有没有从 1.000 掉下来——掉了，这个机制才算有基准支撑。

改了规则后某个机制的数字变了，同步更新这张表和模块 docstring 里的表。
