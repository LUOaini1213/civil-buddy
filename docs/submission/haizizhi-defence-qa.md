# 海之子杯复赛答辩 · 问答准备与口径自查

配套 PPT：05-复赛答辩PPT-CivilBuddy.pptx（14 页 / 600 秒）

**主线**：我们不保证模型不出错，我们保证错的走不出这道门——每一次纠偏都变成一道今天还在拦人、还能当场复跑的门禁。

## 评委可能追问的问题

### 1. 这不就是套壳大模型吗？

正好相反：我们的设计是让模型够不着关键动作。三点可验：① 模型驱动回合里它只能调 8 个工具（update_plan / load_skill / search_kb / list_job_files / read_job_file / run_skill / pack_plan / tender_compare），而让岗位出稿的 run_skill 入参只有 skill_id 与文件名，没有任何自由文本参数——模型写的字在结构上进不了成稿；② 柜数与逐箱 xyz 坐标由确定性引擎算，硬边界写在 tool_registry.py 的模块注释里，不是提示词里求它；③ 聊天轮次一律不能写盘，参数按 schema 校验且拒绝未知键，字段名拼错当场被拒而不是悄悄用默认值。可当场跑 python scripts/test_model_loop.py（27 项）。

### 2. 这些数字哪来的？是不是临演示前手工凑的？

三层回答。① 出处：每个数字背后有一条命令，今天现场可跑——装柜正负例是 main.py --demo 与 --preset structure_fail；招标比对是 eval_tender_response_match.py --variant all；护栏是 eval_verdicts.py --heldout 2。② 防漂移：README 里的扇出数字由 render_eval_table.py --check 对留档 rollup.json 核对，CI 每次提交跑（ci.yml 第 187 行），手打就红灯。③ 常态化：项目门禁 69 项，核心门禁在 CI 每次提交自动跑，不是演示前跑一次。前置条件我也直说：复跑请用仓内 .venv 的 python 并设 PYTHONUTF8=1，用系统 Anaconda 会出假性 FAIL。

### 3. 和现成的装箱软件、标书软件有什么区别？

我们不和求解器比求解，我们补的是求解器两头的活。第一，前面：一句话「尽量少装几个柜」「这批是长料」先落成二十多个显式字段的结构化意图，业务员看得懂、能改，方案为什么长这样说得清。第二，后面：算完不是终点——合规门会判 REJECT 打回，VGM 只出待签字草稿，成稿里每个数字必须指得回工具结果记录，指不回去就点名。第三，它不是单点工具而是 66 个岗位共用一套纪律：同一套数字溯源与结论护栏，既审我们自己出的稿，也能审同事写的、别的 AI 出的稿（civil review，不调模型，退出码 0/1/2）。

### 4. 工地上到底谁用？一线工人会用吗？

分两类人，不混为一谈。项目部和经营口的人用起草那条线，入口有三个：网页工作台、终端命令行、原生桌面窗口（系统自带 Tk，不用另装东西）。一线工人这边，我们今天交付的是给带班的人用的：worker-brief 岗出三分钟班前口播稿，四句话——今天干什么、哪儿会掉会砸会淹、三步怎么干、谁喊停找谁。给工人直接用的手机端一屏一句交底卡、拍照判停、匿名权益问答，材料里写明是设想、未交付，每条都列了还差什么。我们也明确不做面向工人的情绪识别和行为监控打分。

### 5. 66 个岗位是不是吹的？我在你们文档里看到过不一样的数。

先认这一点：仓内 docs/depth-ladder.md 那页确实还写着 L2 66/66，与 README 和申报材料的 36/66 不一致，这是我们文档没改齐，答辩材料一律以更保守的 36/66 为准，这页我们会改齐。分级是：L1 知识库草稿岗 66/66，每岗常见问答≥5、字段表、缺数栏、检索只命中本岗私库，命令 test_kb_k4_depth.py 一次跑出；L2 工具写盘岗 36/66；L3 全链路引擎岗 1 个。另外 66 岗都跑过「能聊」和「能干活」两种模式各 66 通过——但跑得通不等于有本岗专属的成稿栏位，这就是 36 和 66 的差别。

### 6. 真出了事，谁负责？

责任始终在持证的人身上，我们的产品设计就是不让系统替人担责。三条落到代码：① 所有岗位产物带 submit_blocked，而且它是输出格式里的必填常量，不是文档承诺；② 高风险岗位写盘前必须由人原样键入「我明白，将由持证人员签认」，不是点按钮，换任务确认作废；③ VGM 草稿状态是待托运人签字，系统不自动申报。再加一道：结论护栏禁止系统写出「可以订舱」「符合招标要求」这类判定，模型写了先改写、改完还在就划掉点名。定位一句话——内部讨论 AI 草稿，不是签认件。

### 7. 你们举的例子是本机小模型，换个大模型不就没这个问题了？

两点。第一，那两条原话确实来自本机 qwen2.5:3b，我主动说明。第二，这类错和参数量不是一回事：它出错的方式是「数字全对、结论是编的」——每一个数都通过了数字溯源检查，是替人下了一个不该下的判定。所以我们的对策是模型无关的确定性护栏，不是换模型。反过来我们也承认边界：护栏是规则，留出集只有 20 句 9 个必报项，我说的是这一轮的数，不是「不会漏」；数字溯源也只查数在不在，不查标签贴得对不对（比如把柜体额定载重说成货物总重，它查不出）。而且我们把内网小模型才有的失败也补了，比如复读收敛。

### 8. 你们材料里那个大票对照（29→25 柜）怎么今天一个字没提？

因为它现场跑不出来，我就不拿它当今天的论据。那组数依赖本机业务数据 output/cases_446t/materials.json，按仓库 local-only 政策不进仓，净仓环境跑不了；而且我们自己已经把早期的 29 柜基线声明作废，材料里还没清干净，这是我们要改的。今天我用的替代证据是能净仓复跑的那一组：16 车道 × 8 轮 = 128 次流水线，真正装得下 71 次，留档在 docs/eval/fanout16x8-2026-09-02/，数字由 CI 对账。另外补充一句：今天报的数都是 09-13 表头吨/千克那个问题修复之后重跑的。
