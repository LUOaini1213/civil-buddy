# 语音输入评测：术语表修好了什么、没修好什么

语音输入（[docs/voice-input.md](../../docs/voice-input.md)）把一句领域说明和 `demo/asr_lexicon.txt` 里的 35 个术语放进 Whisper 的提示里。这里量两件事：**术语识别到底好了多少、有没有副作用**；以及这些改善里，有多少是术语表的功劳，有多少只是那句领域说明的功劳。

## 怎么量

- **测试句**（`sentences.json`，30 句）：在词表冻结**之后**写的，之后没有根据识别结果回头改过句子或词表。
  - **词表内** 20 句：关键术语都在词表里，看词表修好了什么。
  - **词表外** 10 句：关键术语（抗渗等级、植筋、止水带、滞箱费……）都不在词表里，句子里也不含任何词表词，看词表对没收的术语有没有副作用。
  - `run_eval.py` 会检查这两条划分规则，不满足就报错。
- **音频**（`clips/`，60 段）：每句由两种 Windows 合成音色朗读，编码成 webm/opus，和 Chrome MediaRecorder 实际发给 `/api/asr` 的格式相同，所以也覆盖了真实的解码路径。
  - 本机名为 Kangkang（男声）的音色，实际渲染出来与 Yaoyao 逐字节相同，所以只算两种音色。`make_clips.py` 现在会比对波形，拒绝重复的音色。
- **四种提示**，模型、解码函数都与 `/api/asr` 相同（评测直接调用 `asr.run_model_detail`）：
  - **A**：无提示
  - **B**：只有「以下是普通话的句子。」
  - **C**：B 加一句领域说明「涉及土木施工、投标与装柜物流。」
  - **D**：C 再加 35 个术语，也就是上线配置
  - 所以 **C → D 单看术语表的作用**，B → C 单看领域说明的作用，B → D 是上线配置相对普通话提示的总变化。
- **两种条件**：原始音频；同一段音频加上按片段固定种子的白噪声（SNR 10 dB）。
- **可复现**：Whisper 置信度低时会退回随机采样（temperature > 0）。评测前固定了 CTranslate2 的随机种子，并记录每一次识别有没有发生回退；涉及回退的逐术语变化会标 `*`。
- **指标**：
  - **术语识别率**：关键术语出现在转写里的比例，是主指标。先把转写里的繁体字折算成简体（字表用 OpenCC 生成后固定在脚本里），这样写成繁体不会被算作认错
  - **字错率 CER**：不折算繁简，写成繁体也算错
  - **误插入**：词表里的词在转写中出现的次数超过原句的部分，长词优先计数，所以「装箱单」不会再被重复算成「箱单」
  - **含繁体**：转写里混进繁体字的段数
  - **采样回退**：发生回退的段数
  - **实时率**：识别耗时 ÷ 音频时长，小于 1 表示比说话还快
- **归一化**（参考文本和转写两边一致）：NFKC、去标点和空格、中文数字转阿拉伯数字（四十 → 40）。
- **`--check` 锁定的内容**：每种提示的原文、模型、设备与量化方式、解码参数、噪声 SNR、随机种子、词表、测试句、每段音频的哈希。其中任何一项与现在的代码不一致，CI 就报错，要求重跑评测。

## 结论

1. **改善几乎都来自术语表本身。** 词表内术语在原始音频上：只加领域说明（C）是 55.7%，再加术语表（D）是 **87.1%**。C → D 逐项对比，修好 22 处、**改坏 0 处**。加噪声时从 38.6% 升到 **77.1%**，修好 27 处、改坏 0 处。
2. **那句领域说明单独看作用很小。** 词表内术语在两种条件下，B → C 都只多对了 1 个。词表外术语多对了 2 个（原始音频 30.0% → 36.7%，加噪声 6.7% → 13.3%），在这组里比术语表的贡献还大（C → D 两种条件各修好 1 个）。不过词表外只有 30 个术语出现位置，这几个数只能说明**没有变差**，不能算作提升。
3. **没有看到副作用。** 16 个格子里「误插入词表词」都是 **0**：提示里列了这些词，并没有让模型把没说过的词「听」出来。所有改动里「改坏」都是 0。
4. **普通话提示的作用是写成简体，不是认得更准。** 不加任何提示（A）时，原始音频下有 15/60 段转写混进了繁体字（例如「裝箱單」「拚櫃」）；加了普通话提示后（B），原始音频下是 0/60。把繁体折算成简体再计分，A 和 B 的术语识别率基本一样（词表内 52.9% 对 54.3%），差别在字错率上（17.2% → 11.1%）。上一版评测没做折算，把这部分算成了「A → B 提升 17 个百分点」，那是写法的差异，不是识别能力的差异。
5. **结果可复现。** 480 次识别里没有一次退回随机采样，所以上表每一处逐术语变化都不依赖随机种子。上线配置（D）两种条件下的识别率与上一次评测完全一致；原始音频下没认对的 9 处，连转写原文都和上一次一样（上一次的完整结果已被覆盖，其余转写没法逐条比对）。
6. **没修好的几乎都是同音词。** D 在原始音频下仍然错的 9 处：「订舱 → 订仓」×2、「平柜 → 瓶柜」×2、「坍落度 → 贪落度」×2、「箱单 → 相单」×1、「后浇带 → 交代」×2（后浇带这两处连断句也错了）。提示只能把识别往某个读音推一把，同音的常用词先验更强时就推不动。下一步如果要改进，方向是加一张领域同音纠错表（例如在施工语境里把「订仓」改成「订舱」），而不是继续往提示里加词：提示已经用到 222 / 223 token 了。
7. **词表外的术语仍然很差。** 原始音频下只有 40.0%，加噪声时 16.7%，例如「滞箱费 → 致香费」「高强螺栓 → 高强罗酸」。**术语表只对收进去的词有用**，覆盖面就是它的上限。这也是为什么产品里语音只负责回填文字，由人核对后再发送。
8. **代价是速度。** 加上术语表后，实时率从约 0.42–0.49（C）升到约 0.61–0.68（D），识别耗时多了四成左右；在这台 8 线程的笔记本 CPU 上，一句 5 秒的话要等 3 秒左右。

## 这些数字不能说明什么

- **合成音，不是真人。** 两种 Windows 音色都是标准普通话，吐字清晰。口音、方言、语速不稳、工地噪声都没有测。白噪声条件只是一个粗略的鲁棒性检查，不等于工地环境。
- **词表是我们自己定的，测试句也是我们写的。** 词表内的提升说明「提示里写了的词更容易被认对」，不能证明这张词表覆盖了用户实际会说的话。词表外那组才是在检查副作用。
- **样本小。** 词表内术语共 70 个出现位置（35 个术语 × 2 种音色），词表外 30 个。一个术语的变化，在词表内就是 1.4 个百分点，在词表外是 3.3 个百分点。结果没有给置信区间。
- **只量了本机识别。** 浏览器识别依赖厂商的在线服务，没法离线复现，没有评测。
- **速度是在这一台笔记本 CPU 上测的**（型号见 `results.json` 的 `meta.cpu`），换一台机器数字会不一样。

## 重跑

```bash
pip install -r requirements-asr.txt
python eval/asr/make_clips.py      # 只在改了测试句时需要；要 Windows + PowerShell 7
python eval/asr/run_eval.py        # 约 20 分钟；写 results.json，并更新上面的表
python eval/asr/run_eval.py --limit 2  # 冒烟：只打印，不写任何文件
python eval/asr/run_eval.py --check  # 不需要模型，CI 在跑：核对测试集规则、音频与配置，以及这张表与 results.json 一致
```

改了提示、词表、测试句、音频、模型或解码参数之后，`--check` 会失败，直到重新跑一遍评测。
