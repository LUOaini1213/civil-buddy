一句话：面向土建全链条（投标、施工、出运装柜）的 66 岗智能体工作台。 自然语言召唤专家岗；柜数、坐标等硬数字全部由确定性工具计算，大模型只做理解与路由； 高风险产出必须经过人工审批门；数据读不到会如实说明，不用演示数据冒充结果。

一、场景与痛点（场景创意价值）

建筑企业的日常工作分散在大量「岗位化」的重复劳动里：投标要逐条核对资格条件与废标项、 施工要出安全交底和危大判定、设备物资出运要算装箱拼柜方案。这些工作有三个共同点：

  • 答案必须是可复核的数字或条款，编一个「看起来像」的答案比没有答案更危险；
  • 出错的责任重：柜数算错是真金白银，资格审查漏一条可能废标，方案错了出安全事故；
  • 一线使用者不是程序员：工友、商务、技术员需要的是「说人话就能用」的入口。

Civil Buddy 的回答是：把企业按 16 大类 66 个岗位建成智能体工作台， 每个岗位一份 SOP（skill），用户用一个聊天框召唤任何岗位； 凡是「硬数字」（装箱柜数、三维坐标、重心、利用率），一律交给确定性求解引擎计算， 大模型被明确禁止编造这些数字。装箱拼柜（pack-ship）是其中做得最深的一岗， 背后是一套完整的多智能体装柜引擎。

二、系统架构（技术创新）

自然语言 → 意图理解（IntentSpec） → 岗位路由（66 岗 skill）
        → 白名单工具执行（tools compute numbers；LLM 不写 xyz、不拍柜数）
        → HITL 审批门（高风险产出必须人工确认，Esc/关闭 = 驳回）
        → 影子评测（每次运行留轨迹，128 组自动装箱评测 16×8 扇出）
  • 双栈实现：Rust 工作台（评委下载的 exe，axum，单文件部署）+ Python 参考实现与装箱引擎 （FastAPI + LangGraph）。两栈共享同一套契约文件（contract/*.v1.json 单一来源）， 并有自动对拍测试防止分叉。
  • 装箱引擎：大 Team 编排 ⊃ 小 Team A（材料解析 · 成箱）+ 小 Team B（三维装载 · 重心 · 风险 · 可视化），13 个 Agent 固定专岗，不是自由 multi-agent swarm。 replan 时 critic 与 planner 进行 1～2 轮有界辩论，最终以工具计算结果裁决。
  • 确定性边界：所有坐标、柜数、利用率、重心数字都来自装载求解器； 缺数标 UNSPECIFIED，不允许模型补位。
  • 持续集成：GitHub Actions 双 job（Python 门禁 + cargo test）， 含零外链断网可用、JS 语法、双栈对拍、物料来源诚实性等十余道自动门禁。

四、AI 协同与纠偏管理（AI 协同能力）

人机协同规划

  • 一道审批门：高风险产出（资格判定、写盘、拼柜确认）必须人工点「确认并重提」； Esc 或关闭即驳回，永不默认放行。演示环境也默认 auto_confirm=false。
  • 产出永远是 AI 草稿：每份文书顶部固定声明「内部讨论草稿 · 不是签认件」， 要求持证人员复核签字后方可使用。
  • 预填不自动发送：示例卡只填入输入框，发送永远是人的动作。

AI 纠偏管理（本项目投入最重的部分）

我们认为智能体最大的风险不是「不会做」，而是「做错了还不吭声」。 项目为此建立了「诚实性门禁」体系，并且每道门禁都做过自检（临时回退修复、确认门禁精确报红）：

  • 物料来源诚实性：改造前实测，给一个读不到的表格路径与什么都不给， 系统返回完全相同的演示柜数（15 柜 / 0.675）——静默拿演示数据冒充用户的表。 现在任何一层（exe、网关、SSE 流）读不到表都必须写明 「给了表格路径但读不到——下面的数字不是这张表算出来的」，并有自动化测试钉死。
  • 参数契约纠偏：测试当场逮到「模型把路径放错参数格子则功能静默失效」的缺陷， 修复为多字段兜底 + 契约写死，「模型放错格子不该等于功能静默失效」。
  • 门禁自身的可信度：发现 CI 此前不跑 Rust 测试导致三条断言陈红多轮无人发现， 随即把 cargo test 接入 CI；此类纠偏过程全部记录在 docs/ux/ux-design-spec.md 附录 R，含 AI 自身报错结论被人工复核纠正的实例。
  • 自然语言改方案契约：能改的（改柜型、去材料）返回 applied 并重算； 不能改的（如运费）明确返回「无此功能」，方案不动、不假装成功。

23 轮 UX 迭代与人机协同的完整轨迹（含每轮的纠偏点与 git commit）见仓库 docs/ux/ux-design-spec.md 与随附的人机协同履历表。

五、诚实边界（我们明确不做 / 不宣称的）

  • 所有产出都是内部讨论 AI 草稿，不是法定专项施工方案、不是签认件、不是投标承诺； 涉及结构安全与危大工程的内容必须由持证人员依据正式规范复核签字。
  • 试用包只含工作台本体，不含装箱引擎：输入「装箱」得到的是说明卡； 要看真实柜数需按第三节路径 B 启动引擎。试用包也不含 API Key，需自备。
  • 66 岗按能力诚实分级：L1 知识库 66/66 岗、L2 工具写盘 36/66 岗、L3 引擎深做 1 岗 （pack-ship），每级挂可复跑验收（docs/depth-ladder.md）， 不宣称「66 岗全部深度落地」。
  • 不做：桌面键鼠自动化、微信/飞书集成、CAD 改模、注册工程师签认、 编造条款/单价/坐标。规范全文不进仓库。

六、后续优化计划

  • 两栈路由完全归一（Rust 工作台与 Python 参考实现尚有少量接口差异，已有对拍测试看守）；
  • CI 增加 release 构建产物验证（当前 CI 跑 debug 测试，发布包为 release 构建）；
  • 会话恢复时还原完整 UI 状态（时间线卡、审批卡；当前恢复对话文本）；
  • 装箱引擎向更多岗位输出确定性计算能力（钢筋下料、模板配架等第二个 L3 岗）；
  • 面向工友侧的语音入口与安全交底短视频生成。
